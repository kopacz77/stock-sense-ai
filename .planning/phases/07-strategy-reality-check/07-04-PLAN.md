<objective>
Build a `regime-segmenter` module that takes a full 2018-2025 `BacktestResult` (equity curve + trades) and computes per-regime metrics (Sharpe, MaxDD, win-rate, total trades, etc.) for bull / bear / high-vol regimes per the locked windows in `07-CONTEXT.md`. Includes unit tests because the daily-return-per-sub-window logic is the most subtle correctness risk in this entire phase.

Purpose: `PerformanceMetricsCalculator` operates on whole-backtest data; there's no built-in "metrics for this date slice." Naively splicing discontinuous regime windows (e.g., bull = 2019 + 2020-H2 + 2023 + 2024) inflates volatility because the "jump" between windows is treated as a single-day return. Naively spliced `maxDrawdown` becomes the cross-window peak-to-trough which is not meaningful. This module centralizes the correct handling.

Output: `src/backtesting/analytics/regime-segmenter.ts` exporting `REGIMES`, `sliceByRegime`, `metricsByRegime`. Vitest tests confirming behavior on synthetic equity curves.
</objective>

    Create `src/backtesting/analytics/regime-segmenter.ts`. Import `PerformanceMetricsCalculator` and the relevant types from `../analytics/performance-metrics.js` and `../types/backtest-types.js`.

    **Define types and exports:**

    ```typescript
    export type RegimeName = 'bull' | 'bear' | 'highVol';

    export interface RegimeWindow {
      start: Date;
      end: Date;
    }

    // CONTEXT.md locked regime windows
    export const REGIMES: Record<RegimeName, RegimeWindow[]> = {
      bull: [
        { start: new Date('2019-01-01'), end: new Date('2019-12-31') },
        { start: new Date('2020-07-01'), end: new Date('2020-12-31') },
        { start: new Date('2023-01-01'), end: new Date('2023-12-31') },
        { start: new Date('2024-01-01'), end: new Date('2024-12-31') },
      ],
      bear: [
        { start: new Date('2018-10-01'), end: new Date('2018-12-31') },
        { start: new Date('2022-01-01'), end: new Date('2022-12-31') },
      ],
      highVol: [
        { start: new Date('2020-01-01'), end: new Date('2020-06-30') },
        { start: new Date('2025-01-01'), end: new Date('2025-12-31') },
      ],
    };

    export interface SlicedResult {
      equityCurve: EquityCurvePoint[];      // spliced, sorted by timestamp
      trades: Trade[];                      // trades whose exitDate falls in any window
      contiguousSubWindows: Array<{
        window: RegimeWindow;
        equityCurve: EquityCurvePoint[];    // per-window slice
      }>;
      totalCommissions: number;
      totalSlippage: number;
    }

    export function sliceByRegime(
      equityCurve: EquityCurvePoint[],
      trades: Trade[],
      regime: RegimeName
    ): SlicedResult;

    export function metricsByRegime(
      result: BacktestResult,
      regime: RegimeName
    ): PerformanceMetrics;
    ```

    **`sliceByRegime` implementation rules:**
    1. For each window in `REGIMES[regime]`:
       - Filter `equityCurve` where `point.timestamp >= window.start && point.timestamp <= window.end`. Store this sub-window slice.
       - Filter `trades` where `trade.exitDate >= window.start && trade.exitDate <= window.end` (use `exitDate` for "completed in this regime"; entry-based is less defensible).
    2. Concatenate sub-window equity slices into `equityCurve` (sorted chronologically — they're already in order across non-overlapping windows).
    3. Concatenate trades.
    4. Sum `commission` and `slippage` across the filtered trades for `totalCommissions` / `totalSlippage`.
    5. Return all of the above plus the per-sub-window slices.

    **`metricsByRegime` implementation rules:**
    1. Call `sliceByRegime(result.equityCurve, result.trades, regime)`.
    2. Recompute daily returns **per contiguous sub-window** to avoid cross-window jumps:
       - For each sub-window's equity curve, compute `returns[i] = (equity[i] - equity[i-1]) / equity[i-1]` starting at i=1.
       - Concatenate all sub-window returns into a single `dailyReturns` array. The cross-window "jump" is **NOT** included (it gets implicitly dropped because the first point of each sub-window has no prior in-window predecessor for return calc).
    3. Compute per-sub-window `maxDrawdown` using `PerformanceMetricsCalculator.calculateDrawdowns(subWindow.equityCurve)` and take the **worst** (most negative) across sub-windows. Store as the regime's `maxDrawdown`.
    4. For Sharpe / Sortino / annualized return / other return-based metrics: build a synthetic spliced equity curve from `sliced.equityCurve` (which is already chronologically ordered) but pre-compute `dailyReturns` from step 2 and pass them into `PerformanceMetricsCalculator.calculate` via the appropriate parameter — OR if the calculator computes returns internally, write a small private helper that takes the pre-computed `dailyReturns` and produces Sharpe/Sortino directly (Sharpe = mean(returns) / stddev(returns) * sqrt(252); Sortino = mean(returns) / downside_stddev(returns) * sqrt(252)).

       **Recommended approach:** call `PerformanceMetricsCalculator.calculate(sliced.equityCurve, sliced.trades, sliced.equityCurve[0].equity, firstWindowStart, lastWindowEnd, sliced.totalCommissions, sliced.totalSlippage)` to get most fields, **then override** `maxDrawdown` (from step 3) and `sharpeRatio` / `sortinoRatio` (recomputed from the per-sub-window daily returns of step 2) on the returned object. Annualized return must also be re-derived if it's based on whole-period span (trading-days-in-regime / 252, not calendar-days span).

       Document this clearly with code comments — future-you will thank you.

    5. Handle edge cases:
       - If `sliced.equityCurve` is empty (regime window has zero data), return a zero-filled `PerformanceMetrics` with `totalTrades: 0`. Don't throw.
       - If `sliced.dailyReturns` has length 0 or 1, set Sharpe/Sortino to 0 (avoid div-by-zero).
       - If a sub-window has only 1 equity point, contribute 0 daily returns from that sub-window.

    Add JSDoc explaining the daily-return-per-sub-window design and the maxDrawdown-worst-sub-window choice. Reference RESEARCH.md pitfall #5.

    Create the test file following the existing pattern in `src/data/__tests__/*.test.ts`.

    Use `describe` / `it` / `expect` from vitest.

    **Required test cases:**

    **1. `sliceByRegime` filters equity points correctly**
    - Build a synthetic `equityCurve` with one point per day from 2018-01-01 to 2025-12-31 (use a helper that increments a date and pushes `{ timestamp, equity }` with a flat or linear equity series).
    - Call `sliceByRegime(curve, [], 'bear')`.
    - Assert: every returned `equityCurve` point falls within either `[2018-10-01, 2018-12-31]` or `[2022-01-01, 2022-12-31]`. No 2019 / 2020 / 2023 / 2024 / 2025 points.
    - Assert: `contiguousSubWindows.length === 2`.

    **2. `sliceByRegime` filters trades by exitDate**
    - Build trades with `exitDate` spread across years.
    - Slice by `bull`. Assert: returned trades all have `exitDate` in 2019 / 2020-H2 / 2023 / 2024.

    **3. Daily returns are recomputed per sub-window (no cross-window jumps)**
    - Build an equity curve with:
      - 2019-Q4: equity climbs from 100k → 110k linearly.
      - **GAP** (skip 2020-H1 and parts of 2020-H2).
      - 2020-12: equity continues at 200k.
    - Note: 2019-Q4 is bull, 2020-H1 is high-vol, 2020-H2 is bull.
    - When calling `metricsByRegime(result, 'bull')`:
      - The spliced curve will have a "jump" from 2019-12-31 (equity=110k) to 2020-07-01 (e.g., equity=180k).
      - With naive splicing, daily return at 2020-07-01 would be `(180k - 110k) / 110k = 0.636` → catastrophic Sharpe distortion.
      - **With per-sub-window recomputation:** that jump return is NOT included. Sharpe should be computed only from in-window day-to-day returns.
    - Assert: computed Sharpe is finite and reasonable (e.g., positive for a climbing curve; not blown up by the gap).

    **4. `maxDrawdown` is worst per-sub-window, not cross-window**
    - Construct an equity curve where:
      - 2019: smooth climb 100k → 120k (small drawdowns within).
      - 2023: smooth climb 200k → 220k (small drawdowns within).
      - But the 2019→2023 jump (because 2020-H1 was high-vol, excluded) reflects a 100k → 200k climb in 4 years.
    - Naive cross-window MaxDD might be tiny (curve always rising).
    - Per-sub-window MaxDD captures the largest within-sub-window drawdown.
    - Assert: returned `maxDrawdown` matches the worst single-sub-window drawdown, not 0.

    **5. Edge case: empty regime window data**
    - Call `metricsByRegime` on a curve that has no points in any of the bear windows.
    - Assert: returns a `PerformanceMetrics` with `totalTrades: 0`, `sharpeRatio: 0` (or NaN-safe equivalent), `maxDrawdown: 0`. Does not throw.

    **6. Full-period regime returns same metrics as full backtest (sanity)**
    - Define a custom `REGIMES.test` (just for this test) with one window spanning the entire curve.
    - Call the calculation with that single-window regime and compare to `PerformanceMetricsCalculator.calculate(...)` directly on the same data.
    - Sharpe / win-rate / total-trades should match (within floating-point tolerance for Sharpe).
    - Note: this test may require a small refactor exposing an internal `computeForWindows(windows, curve, trades)` helper rather than hardcoding `REGIMES`. If the public API doesn't allow injecting custom windows, skip this test OR add an internal helper export.

    Run `pnpm test src/backtesting/analytics/__tests__/regime-segmenter.test.ts` to verify all pass.
